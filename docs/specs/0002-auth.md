# 0002 — Auth: device-flow login, session storage, refresh and recovery

- **Status**: draft
- **Owner**: tech-lead (primary session)
- **Depends on**: 0001 (implemented)
- **User docs**: `docs/login.md` (written by this spec's implementation, AC13)

## Context

Every Tidal API call needs a bearer token. tidalt (see `internal/tidal/client.go`, `internal/store/store.go`, `cmd/tidalt/{main,logout,daemon}.go`) did this as follows:

- OAuth2 **device flow** against `https://auth.tidal.com/v1/oauth2` (`/device_authorization`, `/token`, and `/revoke` on logout), with the public client ID and secret of the official Tidal app and scopes `r_usr w_usr w_sub`. Tidal answers `device_authorization` with **camelCase** keys (`deviceCode`, `userCode`, `verificationUri`, `expiresIn`, `interval`), not RFC 8628's snake_case, so tidalt parsed it by hand
- After login it fetched `GET https://api.tidal.com/v1/sessions` for `userId` and `countryCode` (most catalogue calls need `countryCode`)
- The session (tokens, expiry, user ID, country) went into the system keychain, or an age-encrypted file at `~/.config/tidalt/secrets` whose passphrase was read from stdin
- Refresh was delegated to Go's `oauth2.TokenSource`

tidalt's auth worked well overall and this spec keeps its design: the same flow, endpoints and client credentials, keychain first, and an age-encrypted file with a passphrase as the fallback. The gaps below come from reading its code, not from reported failures, and each gets an explicit criterion here:

1. **Refreshed tokens were never saved.** `SaveSession` ran only after an interactive login; refreshes lived in memory and were lost on restart. If Tidal rotates the refresh token, the stored one goes stale → AC6
2. **No recovery when refresh fails.** A revoked or expired refresh token surfaced as failing API calls, with no clear message and no way back short of `logout` + restart → AC7, AC8, AC9
3. **The encrypted-file fallback could only get its passphrase from an interactive stdin prompt**, which a headless daemon (systemd user service) cannot answer → AC16 adds non-interactive passphrase sources; the encryption stays
4. **A failed `/sessions` call silently defaulted the country to `US`**, which gives wrong catalogue results with no error → AC3 (and the extra call is dropped: the token response already carries the user ID and country, see "Facts")
5. **Two processes (daemon + TUI client, or daemon + `login`) shared one stored session but never re-read it**, so a refresh or a new login in one process was invisible to the other → AC8, AC9
6. **`logout` tried to revoke the token, which Tidal refuses** (`403 Request not allowed` for this client, and the token keeps working afterwards; see "Facts"), so the warning always fired and nothing was revoked → logout only deletes locally

## Behaviour

### Commands

| Command | What it does |
|---|---|
| `tidal-player login` | Runs the device flow in the terminal (no TUI): prints the verification URL and user code, tries to open the URL in a browser (failure is ignored), polls until the user approves, takes the user ID and country from the token response, saves the session and prints `Logged in as user <id> (<country>)`. Exit 0 on success. Replaces any existing session |
| `tidal-player logout` | Deletes the stored session from every store and prints `Logged out`. It does not contact Tidal: revocation is refused for this client (see "Facts"), so the login stays valid server-side until Tidal expires it, but no copy of it remains on this machine. Exit 0 even when nothing was stored (`Not logged in`) |
| `tidal-player` (standalone, no stored session) | Prints `Not logged in.` and runs the same flow as `login` before entering the TUI. Ctrl-C during the flow exits 130 without touching the terminal mode |
| `tidal-player daemon` (no stored session) | Exits 1 with `Not logged in: run "tidal-player login"`. It never starts an interactive flow |

The login prompt (plain stdout, before any TUI):

```
To log in, open this link and approve the code:

  https://link.tidal.com

Code: ABCDE   (expires in 5 min)
Waiting for approval… (Ctrl-C to cancel)
```

`verificationUri` comes back without a scheme, so `https://` is prepended. The printed link is always the plain `https://<verificationUri>` plus the code, which is the path verified on the live API. The browser is opened on `https://<verificationUriComplete>` when the response has it (it may pre-fill the code; not verified), else on the plain link. The minutes come from `expiresIn` (300 s on the live API).

### Session

A stored session holds: access token, refresh token, absolute expiry time (UTC, computed at receipt from `expires_in`), user ID, country code. It is serialised as versioned JSON (`{"version":1,…}`); an unknown version or unparseable data is treated as "not logged in" and logged, never as a crash.

### Storage

- **Primary**: the Secret Service via `keyring` (service `tidal-player`, account `session`)
- **Fallback**, when the Secret Service is unavailable (no D-Bus session bus, no provider running, locked and not unlockable without a prompt): `$XDG_STATE_HOME/tidal-player/session.age` (default `~/.local/state/tidal-player/session.age`), **encrypted with a passphrase** in the [age](https://age-encryption.org) format (scrypt recipient), as tidalt did. Created with mode `0600` in a directory with mode `0700`, written atomically (temp file + rename)
- **Passphrase sources**, first match wins:
  1. `TIDAL_PLAYER_PASSPHRASE_FILE` (path to a file whose first line is the passphrase)
  2. systemd credentials: `$CREDENTIALS_DIRECTORY/tidal-player-passphrase` (set by `LoadCredential=`/`LoadCredentialEncrypted=` in the unit; the unit itself is spec 0005)
  3. an interactive prompt with echo off, only when stdin and stderr are terminals: `Passphrase for the tidal-player session:`. When the file is first created the prompt asks twice (`Confirm passphrase:`) and retries on mismatch. A wrong passphrase re-prompts, up to 3 attempts
  4. none of the above → the encrypted store is unusable: `daemon` exits 1 with `Session file is encrypted and no passphrase is available: set TIDAL_PLAYER_PASSPHRASE_FILE or a systemd credential (see docs/login.md)`
- The passphrase is asked **once per process** and held in memory (zeroised on drop) so refreshed tokens can be re-encrypted without asking again (AC6). It is never logged
- There is deliberately no `TIDAL_PLAYER_PASSPHRASE` variable holding the passphrase itself: environment variables leak through `/proc/<pid>/environ` and child processes
- Reads try the keyring first, then the file. Writes go to whichever backend is available, keyring first. `logout` deletes from both
- Which backend is in use is logged at `info`, never printed while the TUI is up
- Environment variables, documented in `docs/login.md`: `TIDAL_PLAYER_PASSPHRASE_FILE` (above), `TIDAL_PLAYER_STATE_DIR` overrides the state directory, and `TIDAL_PLAYER_NO_KEYRING=1` skips the keyring entirely (for machines without a Secret Service, and for tests)

### Using and refreshing the session

All authenticated requests go through one `Authenticator` per process, which owns the in-memory session:

- **Proactive refresh**: before a request, if the access token expires within **60 s** (or already has), refresh first
- **Reactive refresh**: if a request returns **401**, refresh once and retry the request once. A second 401 is returned as an error, no loop
- **Single flight**: concurrent requests that need a refresh share one refresh call
- **Persist on refresh**: every successful refresh writes the session back to storage immediately, keeping the old refresh token when the response omits one and replacing it when the response carries a new one
- **Cross-process pickup**: before refreshing, re-read storage; if the stored session has a later expiry than the in-memory one (another process refreshed or logged in), adopt it and skip the refresh

### When refresh fails

Refresh failures are classified:

| Response | Kind | What happens |
|---|---|---|
| `400`/`401` with `error` = `invalid_grant` or `invalid_client`, or `401` without a body | **Session lost** | Re-read storage once (another process may have a newer refresh token); if it holds a different refresh token, adopt it and try once more. Otherwise the session is lost: the stored session is **kept** (so a later `login` from another process can be told apart from it, AC9), API calls fail fast with `AuthError::LoginRequired` without network traffic, and the player broadcasts `Event::LoginRequired` |
| network error, timeout, `5xx`, `429` | **Transient** | The request fails with a transient error; the session stays valid; the next request tries to refresh again. No `LoginRequired` |

Recovery from "session lost": run `tidal-player login` (from any terminal, also while a daemon or TUI is running). A process in the "session lost" state re-reads storage on each API call (throttled to once per 5 s) and leaves the state as soon as it finds a session with a different refresh token. The player then broadcasts `Event::LoginRestored`.

### In the TUI

`Event::LoginRequired` shows a persistent status line `Session expired — run "tidal-player login" in another terminal`; `Event::LoginRestored` clears it. Logging in from inside the TUI is out of scope.

### Secrets hygiene

Tokens never appear in logs, panic messages, `Debug` output or error messages. `Session`'s `Debug` prints `"<redacted>"` for both tokens.

## Acceptance criteria

Device flow (`tidal-player-api::auth`):

- **AC1** — `start_device_flow` sends `POST {auth_base}/device_authorization` with form fields `client_id` and `scope=r_usr w_usr w_sub`, and parses Tidal's camelCase response into `DeviceCode { device_code, user_code, verification_uri, verification_uri_complete: Option<_>, expires_in, interval }`; `login_link` gives `https://link.tidal.com` and `browser_link` gives `https://link.tidal.com/ABCDE` for the recorded fixture, and the plain link when `verificationUriComplete` is absent
- **AC2** — Polling `POST {auth_base}/token` (`grant_type=urn:ietf:params:oauth:grant-type:device_code`, client credentials, `device_code`) maps each response to a `PollOutcome`: `authorization_pending` → keep polling at the same interval; `slow_down` → keep polling with the interval increased by 5 s; `expired_token` → `AuthError::CodeExpired`; `access_denied` → `AuthError::Denied`; `200` → tokens. Polling stops with `CodeExpired` once `expires_in` has elapsed, even if the server still says pending
- **AC3** — The session's `user_id` comes from the token response's top-level `user_id` and `country_code` from `user.countryCode`, both on login and on every refresh (so a changed country is picked up). If either is missing or the country is empty, login fails with `AuthError::SessionInfo` and nothing is stored (no `US` default); a refresh with them missing keeps the previous values and logs a warning. No `/v1/sessions` call is made

Session & refresh (`tidal-player-api::auth`):

- **AC4** — `needs_refresh(session, now)` is true iff `expires_at - now < 60 s` (table: far future, exactly 60 s, 59 s, expired)
- **AC5** — An authenticated request with a fresh token sends `Authorization: Bearer <access>`; with a token inside the 60 s window it refreshes first (`grant_type=refresh_token`) and sends the new token; on a `401` it refreshes once and retries once; a second `401` returns `AuthError::Unauthorized` after exactly two attempts. N concurrent requests needing a refresh cause exactly one refresh call
- **AC6** — Every successful refresh writes the new session to the `SessionStore` before the retried request is sent. A refresh response without `refresh_token` keeps the old one; one with `refresh_token` replaces it
- **AC7** — Refresh failures are classified as in the "When refresh fails" table (table-driven over status + body). "Session lost" makes the `Authenticator` return `AuthError::LoginRequired` for later calls **without sending a request**, and keeps the stored session. "Transient" leaves the session usable, and the next call refreshes again
- **AC8** — Cross-process: (a) before refreshing, a stored session with a later expiry is adopted and no refresh is sent; (b) on "session lost", a stored session with a different refresh token is adopted and refreshed once before giving up
- **AC9** — A process in the "session lost" state that finds a session with a different refresh token in storage (re-read at most once per 5 s) leaves the state and serves requests with it again

Storage (`tidal-player` binary):

- **AC10** — `EncryptedFileStore` round-trips a session with the right passphrase; the file on disk is an age file (starts with `age-encryption.org/v1`) and contains no token in plaintext; a wrong passphrase on load returns `StoreError::WrongPassphrase` (never `None`, so the caller re-prompts rather than starting a new login); creates the file with mode `0600` and its directory with `0700`; writes atomically (a crash between write and rename leaves the old file intact); treats a missing file as `None`, and a correctly decrypted but unparseable JSON or unknown `version` as `None` with a logged warning; `delete` on a missing file succeeds, and `delete` never needs the passphrase
- **AC11** — `FallbackStore` (keyring first, encrypted file second, both behind the `SessionStore` trait): when the primary errors with "unavailable", load/save/delete go to the secondary; `delete` removes from both; `load` returns the primary's session if it has one, else the secondary's

CLI, protocol and UI:

- **AC12** — `tidal-player daemon` with an empty store exits 1 and stderr contains `tidal-player login`; `tidal-player logout` with an empty store exits 0 and prints `Not logged in`, and with a stored session deletes it and sends no HTTP request (no `/revoke`); `tidal-player daemon` with an encrypted session file, no passphrase source and no terminal exits 1 and stderr names `TIDAL_PLAYER_PASSPHRASE_FILE`
- **AC13** — `docs/login.md` documents `login`, `logout`, where the session is stored, the passphrase and how to give it to the daemon (passphrase file, systemd credential), and what "session expired" means and how to recover; this spec links to it
- **AC14** — `Command`/`Event` gain `Event::LoginRequired` and `Event::LoginRestored` (round-trip table of AC11 in spec 0001 extended). `ui::update` on `LoginRequired` sets the status line and on `LoginRestored` clears it; `render` at 80×24 with the status line set matches a snapshot
- **AC16** — `resolve_passphrase` picks the source in the order given under "Passphrase sources" (table: file var set, credentials dir set, both set, neither + terminal, neither + no terminal); a passphrase file's trailing newline is stripped; an empty passphrase is rejected; with no source and no terminal it returns `PassphraseError::Unavailable` and the message names `TIDAL_PLAYER_PASSPHRASE_FILE`. The prompt itself sits behind a `Prompt` trait faked in tests (wrong-then-right → 2 calls; 3 wrong → `WrongPassphrase`; confirm mismatch → asks again)
- **AC15** — `format!("{session:?}")` contains neither token's value; `AuthError`'s `Display` for every variant contains no token, even when built from a server body that echoes one

## Edge cases & errors

- **Ctrl-C during `login`**: the poll loop is cancelled, nothing is stored, exit 130
- **Code expires** before approval: `Login code expired, run "tidal-player login" again`, exit 1 (AC2)
- **User denies** on the Tidal page: `Login was denied`, exit 1 (AC2)
- **No network during `login`**: the poll treats transport errors as transient and keeps polling until `expires_in`; the start request failing exits 1 with the transport error
- **Clock skew**: the expiry is computed from `expires_in` at receipt, not from a server timestamp; the 60 s margin plus the reactive 401 path cover small skews
- **Secret Service locked**: treated as unavailable (no unlock prompt from a daemon), so the file fallback is used. A later unlock does not migrate the session; both stores are read on load
- **Corrupted / foreign data** in either store: treated as not logged in (AC10)
- **Forgotten passphrase**: `tidal-player logout` deletes the encrypted file without asking for it; then `login` starts over (AC10)
- **A transport error on the very first poll** happened once on the live API (curl got no response) while later polls with the same request succeeded: transport errors while polling are transient (see "No network during `login`")
- **Wrong passphrase in the daemon** (passphrase file out of date): exit 1 with `Wrong passphrase for the session file`, not "not logged in", so the session file is never overwritten by mistake (AC10, AC16)
- **Passphrase file readable by others**: warn (`passphrase file is readable by other users`) but use it
- **`logout` while a daemon runs**: the daemon's next refresh or 401 hits "session lost" (AC7); its next `login` is picked up (AC9)
- **Free / non-HiFi accounts**: login succeeds; what they can stream is spec 0003's concern

## Crate placement

- `tidal-player-core`: `Event::LoginRequired`/`LoginRestored`, the UI status line. No HTTP, no storage
- `tidal-player-api::auth`: `Session`, `DeviceCode`, `PollOutcome`, `AuthError`, the pure classifiers, the `SessionStore` trait + `MemoryStore` (for tests and as a building block), `Authenticator`. Base URLs injected (`auth_base`, `api_base`); production URLs as named constants

## Facts vs. assumptions

Verified on 2026-10-06 against the **live API** by `scripts/tidal-auth-probe.sh`, run by the user with a real account (tokens and IDs redacted; fixtures under `crates/api/tests/fixtures/auth/` are written from these shapes with fake values):

- **Device authorization** `200`: `{deviceCode, userCode (5 chars), verificationUri: "link.tidal.com", verificationUriComplete: "link.tidal.com/<userCode>", expiresIn: 300, interval: 2}`. Opening `https://link.tidal.com` and typing the code works
- **Pending poll**: `400 {"error":"authorization_pending","error_description":"Device Authorization code is not authorized yet","status":400,"sub_status":1002}`. `slow_down` was not seen
- **Granted** `200`: `{access_token, refresh_token, token_type, expires_in: 14400, scope, clientName: "Android Automotive HiRes", user_id: <number>, user: {userId, countryCode, email, username, …}}`. Access tokens last **4 hours**
- **Refresh** `200`: same shape **without `refresh_token`**: Tidal does not rotate it, the original one stays valid
- **Bad refresh token**: `400 {"error":"invalid_grant","error_description":"Token has invalid payload","status":400,"sub_status":1005}`
- **API call with a bad bearer** (`GET /v1/sessions`): `401 {"status":401,"subStatus":11002,"userMessage":"Token has invalid payload"}`: API errors use a different body shape from `/token` errors and have no `error` key
- **Revoke** (`POST /revoke`, basic auth, as tidalt did): `403 {"error_description":"Request not allowed","status":403,"sub_status":1005}`, and the refresh token still refreshed afterwards (`200`). Revocation does not work for this client
- `GET /v1/sessions` works (`userId`, `countryCode`, `sessionId`, …) but adds nothing the token response lacks
- One transport failure (no HTTP response) on the first poll, right after `device_authorization`; the following polls were fine

Not verified, and how the spec copes:

- `slow_down`, `expired_token`, `access_denied` bodies: assumed RFC 8628 error codes in the same `{"error":…}` shape as `authorization_pending`; fixtures are hand-written to that shape and marked as such
- Whether `verificationUriComplete` pre-fills the code: only used for the browser, the printed instructions don't rely on it
- The response for a refresh token Tidal has actually expired or invalidated server-side (could not be produced, since revoke is refused): assumed to be the `invalid_grant` shape above
- `keyring` 4 on Linux reaches the Secret Service over D-Bus without native libraries and reports "no provider" as a distinguishable error (needed by AC11)

## Decisions (answered by the user, 2026-10-06)

1. **File fallback**: encrypted with a passphrase, as tidalt did. The daemon gets its passphrase from a file or a systemd credential (AC16)
2. **Client credentials**: the official Tidal app's public client ID and secret, as tidalt used them, as named constants in `tidal-player-api::auth`
3. **First run without a session**: run the login flow inline before the TUI
4. No further tidalt auth bugs reported; tidalt's auth is considered good, and this spec keeps its design

## Out of scope

- Logging in from inside the TUI (QR code, in-TUI device code)
- Multiple accounts / profile switching
- PKCE / browser-redirect login (only the device flow)
- Configurable client credentials (decision 2; may revisit in 0008)
- Migrating an existing tidalt session (`~/.config/tidalt/secrets`): users log in again once
- How the daemon broadcasts `Event`s to clients (transport is 0005; this spec only adds the variants and the player-side decision)
- Stream quality and subscription-tier handling (0003)
