# 0002 — 認證：device flow 登入、工作階段儲存、更新與復原

- **狀態**：implemented（2026-10-07）
- **負責人**：tech-lead（主要工作階段）
- **相依於**：0001（implemented）
- **使用者文件**：[`docs/login.md`](../../zh-TW/login.md)（由本規格的實作撰寫，AC13）

<a id="context"></a>
## 背景

每個 Tidal API 呼叫都需要 bearer 權杖。tidalt（見 `internal/tidal/client.go`、`internal/store/store.go`、`cmd/tidalt/{main,logout,daemon}.go`）是這樣做的：

- 對 `https://auth.tidal.com/v1/oauth2` 進行 OAuth2 **device flow**（`/device_authorization`、`/token`，登出時用 `/revoke`），使用官方 Tidal 應用程式的公開 client ID 與 secret，以及 scope `r_usr w_usr w_sub`。Tidal 對 `device_authorization` 回應的是 **camelCase** 的鍵（`deviceCode`、`userCode`、`verificationUri`、`expiresIn`、`interval`），而不是 RFC 8628 的 snake_case，所以 tidalt 用手工解析
- 登入後它取得 `GET https://api.tidal.com/v1/sessions`，以得到 `userId` 與 `countryCode`（大多數曲庫呼叫都需要 `countryCode`）
- 工作階段（權杖、到期時間、使用者 ID、國家）存入系統金鑰圈，或存入 `~/.config/tidalt/secrets` 的 age 加密檔案，其密碼從 stdin 讀取
- 更新（refresh）交給 Go 的 `oauth2.TokenSource` 處理

tidalt 的認證整體運作良好，本規格保留它的設計：相同的流程、端點與 client 憑證，金鑰圈優先，並以附密碼的 age 加密檔案作為後備方案。下列缺口來自閱讀它的程式碼，而不是來自回報的故障，每一項在這裡都有明確的條件：

1. **更新後的權杖從未被儲存。** `SaveSession` 只在互動式登入之後執行；更新只存在記憶體中，重新啟動就遺失了。若 Tidal 輪替 refresh 權杖，儲存的那一個就會過期 → AC6
2. **更新失敗時沒有復原方式。** 被撤銷或過期的 refresh 權杖只表現為失敗的 API 呼叫，沒有清楚的訊息，除了 `logout` 加重新啟動之外沒有辦法回復 → AC7、AC8、AC9
3. **加密檔案的後備方案只能透過互動式的 stdin 提示取得密碼**，而無畫面的常駐程式（systemd 使用者服務）無法回答 → AC16 加入非互動式的密碼來源；加密本身不變
4. **失敗的 `/sessions` 呼叫會悄悄地把國家預設為 `US`**，造成錯誤的曲庫結果卻沒有任何錯誤 → AC3（並且去掉這個多餘的呼叫：權杖回應已經帶有使用者 ID 與國家，見「事實與假設」）
5. **兩個行程（常駐程式加 TUI 客戶端，或常駐程式加 `login`）共用一個儲存的工作階段，卻從不重新讀取它**，所以一個行程中的更新或新登入對另一個是不可見的 → AC8、AC9
6. **`logout` 嘗試撤銷權杖，但 Tidal 拒絕了**（對這個 client 是 `403 Request not allowed`，且權杖之後仍可使用；見「事實與假設」），所以警告總是會觸發，卻什麼都沒有被撤銷 → logout 只在本機刪除

<a id="behaviour"></a>
## 行為

<a id="commands"></a>
### 指令

| 指令 | 作用 |
|---|---|
| `tidal-player login` | 在終端機中執行 device flow（沒有 TUI）：印出驗證 URL 與使用者代碼，嘗試在瀏覽器中開啟該 URL（失敗則忽略），輪詢直到使用者核准，從權杖回應取得使用者 ID 與國家，儲存工作階段並印出 `Logged in as user <id> (<country>)`。成功時結束碼為 0。取代任何既有的工作階段 |
| `tidal-player logout` | 從每個儲存位置刪除儲存的工作階段，並印出 `Logged out`。它不會聯絡 Tidal：這個 client 的撤銷會被拒絕（見「事實與假設」），所以該登入在伺服器端仍然有效，直到 Tidal 使它過期，但這台機器上不會留下任何副本。即使什麼都沒儲存（`Not logged in`），結束碼仍為 0 |
| `tidal-player`（獨立模式，沒有儲存的工作階段） | 印出 `Not logged in.`，並在進入 TUI 之前執行與 `login` 相同的流程。流程中按 Ctrl-C 會以 130 結束，且不動終端機模式 |
| `tidal-player daemon`（沒有儲存的工作階段） | 以 1 結束，並印出 `Not logged in: run "tidal-player login"`。它絕不會啟動互動式流程 |

登入提示（純 stdout，在任何 TUI 之前）：

```
To log in, open this link and approve the code:

  https://link.tidal.com

Code: ABCDE   (expires in 5 min)
Waiting for approval… (Ctrl-C to cancel)
```

`verificationUri` 回來時不帶協定（scheme），所以會在前面加上 `https://`。印出的連結一律是單純的 `https://<verificationUri>` 加上代碼，這是在真實 API 上驗證過的路徑。回應中有 `verificationUriComplete` 時，瀏覽器會開啟 `https://<verificationUriComplete>`（它可能預先填入代碼；未驗證），否則開啟單純的連結。分鐘數來自 `expiresIn`（真實 API 上為 300 秒）。

<a id="session"></a>
### 工作階段

儲存的工作階段包含：access 權杖、refresh 權杖、絕對到期時間（UTC，於收到時由 `expires_in` 計算）、使用者 ID、國家代碼。它序列化為有版本的 JSON（`{"version":1,…}`）；未知的版本或無法解析的資料會被視為「未登入」並記錄下來，絕不會導致當機。

<a id="storage"></a>
### 儲存

- **主要**：透過 `keyring` 使用 Secret Service（service 為 `tidal-player`，account 為 `session`）
- **後備**，在 Secret Service 不可用時（沒有 D-Bus session bus、沒有執行中的提供者、已鎖定且無法在不提示的情況下解鎖）：`$XDG_STATE_HOME/tidal-player/session.age`（預設為 `~/.local/state/tidal-player/session.age`），以 [age](https://age-encryption.org) 格式（scrypt 收件者）**用密碼加密**，與 tidalt 相同。以模式 `0600` 建立，位於模式 `0700` 的目錄中，以原子方式寫入（暫存檔加 rename）
- **密碼來源**，第一個符合的優先：
  1. `TIDAL_PLAYER_PASSPHRASE_FILE`（檔案路徑，檔案的第一行即密碼）
  2. systemd 憑證：`$CREDENTIALS_DIRECTORY/tidal-player-passphrase`（由 unit 中的 `LoadCredential=`/`LoadCredentialEncrypted=` 設定；unit 本身是 spec 0005）
  3. 關閉回顯的互動式提示，僅在 stdin 與 stderr 都是終端機時：`Passphrase for the tidal-player session:`。第一次建立檔案時，提示會問兩次（`Confirm passphrase:`），不一致時重試。密碼錯誤會重新提示，最多 3 次
  4. 以上皆無 → 加密的儲存位置無法使用：`daemon` 以 1 結束，並印出 `Session file is encrypted and no passphrase is available: set TIDAL_PLAYER_PASSPHRASE_FILE or a systemd credential (see docs/login.md)`
- 密碼**每個行程只詢問一次**並保留在記憶體中（釋放時清零），這樣更新後的權杖就能重新加密而不必再問（AC6）。它絕不會被記錄
- 刻意不提供直接存放密碼本身的 `TIDAL_PLAYER_PASSPHRASE` 變數：環境變數會透過 `/proc/<pid>/environ` 與子行程洩漏
- 讀取先試金鑰圈，再試檔案。寫入到任何可用的後端，金鑰圈優先。`logout` 兩者都刪除
- 使用哪個後端會以 `info` 記錄，TUI 開啟期間絕不印出
- 環境變數，記載於 `docs/login.md`：`TIDAL_PLAYER_PASSPHRASE_FILE`（見上），`TIDAL_PLAYER_STATE_DIR` 覆寫狀態目錄，以及 `TIDAL_PLAYER_NO_KEYRING=1` 完全略過金鑰圈（供沒有 Secret Service 的機器與測試使用）

<a id="using-and-refreshing-the-session"></a>
### 使用與更新工作階段

所有需要認證的請求都經過每個行程一個的 `Authenticator`，由它擁有記憶體中的工作階段：

- **主動更新**：請求之前，若 access 權杖會在 **60 秒**內到期（或已經到期），先更新
- **被動更新**：若請求回傳 **401**，更新一次並重試該請求一次。第二次 401 會作為錯誤回傳，不會迴圈
- **Single flight**：需要更新的並行請求共用同一次更新呼叫
- **更新時持久化**：每次成功的更新都立即把工作階段寫回儲存位置；回應省略 refresh 權杖時保留舊的，回應帶有新的時則取代
- **更新用的 client**（AC19）：每次更新，以及登入之後立即的一次更新，都使用官方 Android 應用程式的 PKCE client（`6BDSRdpK9hqEBTgU`，即 `tidalapi` 隨附的 `client_id_pkce`），而不是登入所用的 device-flow client。發給 device-flow client 的權杖拿到的是 AAC，而不是 16 位元 FLAC（見「錯誤」）。若 Tidal 拒絕 PKCE client 本身（`invalid_client` / `unauthorized_client`，不是 `invalid_grant`），就改用登入的 client 更新，並記錄一則警告：CD 音質的曲目會是有損的；這不算「工作階段遺失」
- **跨行程取用**：更新之前先重新讀取儲存位置；若儲存的工作階段到期時間比記憶體中的晚（另一個行程已更新或已登入），就採用它並略過更新

<a id="when-refresh-fails"></a>
### 更新失敗時

更新失敗會被分類：

| 回應 | 種類 | 會發生什麼 |
|---|---|---|
| `400`/`401` 且 `error` 為 `invalid_grant`、`invalid_client` 或 `unauthorized_client`（對於 client 代碼：在 AC19 退回 device-flow client 也被拒絕之後），或沒有本文的 `401` | **工作階段遺失** | 重新讀取儲存位置一次（另一個行程可能有較新的 refresh 權杖）；若它持有不同的 refresh 權杖，就採用它並再試一次。否則工作階段即遺失：儲存的工作階段會被**保留**（這樣之後從另一個行程進行的 `login` 才能與它區分，AC9），API 呼叫會在不產生網路流量的情況下以 `AuthError::LoginRequired` 快速失敗，且播放器會廣播 `Event::LoginRequired` |
| 網路錯誤、逾時、`5xx`、`429`，以及上面未列出的任何其他回應（例如 `403`、帶有其他 `error` 代碼的 `400`） | **暫時性** | 請求以暫時性錯誤失敗；工作階段仍然有效；下一個請求會再次嘗試更新。不會有 `LoginRequired` |

從「工作階段遺失」復原：執行 `tidal-player login`（可從任何終端機，常駐程式或 TUI 執行中也可以）。處於「工作階段遺失」狀態的行程會在每次 API 呼叫時重新讀取儲存位置（節流為每 5 秒一次），一找到 refresh 權杖不同的工作階段就離開該狀態。然後播放器會廣播 `Event::LoginRestored`。

<a id="in-the-tui"></a>
### 在 TUI 中

`Event::LoginRequired` 會顯示一行持續存在的狀態列 `Session expired — run "tidal-player login" in another terminal`；`Event::LoginRestored` 會清除它。從 TUI 內部登入不在範圍內。

<a id="secrets-hygiene"></a>
### 機密資料的衛生

權杖絕不會出現在記錄、panic 訊息、`Debug` 輸出或錯誤訊息中。`Session` 的 `Debug` 對兩個權杖都印出 `"<redacted>"`。

<a id="acceptance-criteria"></a>
## 驗收條件

Device flow（`tidal-player-api::auth`）：

- **AC1** — `start_device_flow` 送出 `POST {auth_base}/device_authorization`，表單欄位為 `client_id` 與 `scope=r_usr w_usr w_sub`，並把 Tidal 的 camelCase 回應解析為 `DeviceCode { device_code, user_code, verification_uri, verification_uri_complete: Option<_>, expires_in, interval }`；對於錄製的測試資料，`login_link` 給出 `https://link.tidal.com`，`browser_link` 給出 `https://link.tidal.com/ABCDE`，而 `verificationUriComplete` 不存在時則給出單純的連結
- **AC2** — 輪詢 `POST {auth_base}/token`（`grant_type=urn:ietf:params:oauth:grant-type:device_code`、client 憑證、`device_code`）會把每個回應對應到一個 `PollOutcome`：`authorization_pending` → 以相同的間隔繼續輪詢；`slow_down` → 間隔增加 5 秒後繼續輪詢；`expired_token` → `AuthError::CodeExpired`；`access_denied` → `AuthError::Denied`；`200` → 權杖。一旦 `expires_in` 已經過去，即使伺服器仍說 pending，輪詢也以 `CodeExpired` 停止
- **AC3** — 工作階段的 `user_id` 來自權杖回應最上層的 `user_id`，`country_code` 來自 `user.countryCode`，登入與每次更新都是如此（因此變更的國家會被取得）。若其中一個缺少或國家為空，登入以 `AuthError::SessionInfo` 失敗且不儲存任何東西（沒有 `US` 預設值）；缺少它們的更新會保留先前的值並記錄一則警告。不會發出 `/v1/sessions` 呼叫

工作階段與更新（`tidal-player-api::auth`）：

- **AC4** — 當且僅當 `expires_at - now < 60 s` 時，`needs_refresh(session, now)` 為真（表格：遙遠的未來、剛好 60 秒、59 秒、已過期）
- **AC5** — 帶有新鮮權杖的已認證請求會送出 `Authorization: Bearer <access>`；權杖落在 60 秒視窗內時，會先更新（`grant_type=refresh_token`）再送出新權杖；遇到 `401` 時更新一次並重試一次；第二個 `401` 在恰好兩次嘗試之後回傳 `AuthError::Unauthorized`。N 個需要更新的並行請求只會造成恰好一次更新呼叫
- **AC6** — 每次成功的更新，都在送出重試的請求之前，把新的工作階段寫入 `SessionStore`。沒有 `refresh_token` 的更新回應會保留舊的；帶有 `refresh_token` 的則取代它
- **AC7** — 更新失敗依「更新失敗時」表格分類（表格驅動，依狀態加本文）。「工作階段遺失」會讓 `Authenticator` 對之後的呼叫回傳 `AuthError::LoginRequired` 而**不送出請求**，並保留儲存的工作階段。「暫時性」讓工作階段保持可用，下一次呼叫會再次更新
- **AC8** — 跨行程：(a) 更新之前，到期時間較晚的儲存工作階段會被採用，且不送出更新；(b) 在「工作階段遺失」時，refresh 權杖不同的儲存工作階段會被採用，並在放棄之前更新一次
- **AC9** — 處於「工作階段遺失」狀態的行程，若在儲存位置（最多每 5 秒重新讀取一次）找到 refresh 權杖不同的工作階段，就離開該狀態並再次以它處理請求

儲存（`tidal-player` 執行檔）：

- **AC10** — `EncryptedFileStore` 以正確的密碼往返一個工作階段；磁碟上的檔案是 age 檔案（以 `age-encryption.org/v1` 開頭），且不含明文權杖；載入時密碼錯誤會回傳 `StoreError::WrongPassphrase`（絕不是 `None`，這樣呼叫端會重新提示，而不是開始新的登入）；以模式 `0600` 建立檔案、以 `0700` 建立其目錄；以原子方式寫入（寫入與 rename 之間當機，舊檔案仍完好）；遺失的檔案視為 `None`，而正確解密但無法解析的 JSON 或未知的 `version` 視為 `None` 並記錄一則警告；對遺失的檔案 `delete` 會成功，且 `delete` 絕不需要密碼
- **AC11** — `FallbackStore`（金鑰圈優先、加密檔案其次，兩者都在 `SessionStore` trait 之後）：當主要儲存位置以「unavailable」出錯時，load/save/delete 會轉到次要的；`delete` 從兩者移除；`load` 若主要的有工作階段就回傳它，否則回傳次要的

CLI、協定與 UI：

- **AC12** — 儲存位置為空時，`tidal-player daemon` 以 1 結束，且 stderr 含有 `tidal-player login`；儲存位置為空時，`tidal-player logout` 以 0 結束並印出 `Not logged in`，有儲存的工作階段時則刪除它且不送出任何 HTTP 請求（沒有 `/revoke`）；有加密的工作階段檔案、沒有密碼來源且沒有終端機時，`tidal-player daemon` 以 1 結束，且 stderr 指名 `TIDAL_PLAYER_PASSPHRASE_FILE`
- **AC13** — `docs/login.md` 記載 `login`、`logout`、工作階段儲存的位置、密碼以及如何提供給常駐程式（密碼檔、systemd 憑證），還有「session expired」的意義與如何復原；本規格連結到它
- **AC14** — `Command`/`Event` 新增 `Event::LoginRequired` 與 `Event::LoginRestored`（擴充 spec 0001 中 AC11 的往返表格）。`ui::update` 在 `LoginRequired` 時設定狀態列，在 `LoginRestored` 時清除它；設定了狀態列的 80×24 `render` 與快照相符
- **AC16** — `resolve_passphrase` 依「密碼來源」所列的順序挑選來源（表格：設定了檔案變數、設定了憑證目錄、兩者都設定、兩者都沒有加終端機、兩者都沒有且沒有終端機）；密碼檔結尾的換行會被去除；空密碼會被拒絕；沒有來源且沒有終端機時回傳 `PassphraseError::Unavailable`，且訊息指名 `TIDAL_PLAYER_PASSPHRASE_FILE`。提示本身位於 `Prompt` trait 之後，在測試中以假實作（fake）取代（錯的再對的 → 2 次呼叫；3 次錯誤 → `WrongPassphrase`；確認不一致 → 再問一次）
- **AC17** — 設定了登入狀態列的 `render` 在極小的終端機上絕不 panic：只有在邊框內部區域至少有一列（高度 ≥ 3）時，狀態列才畫在邊框內的最後一列；更小的終端機不顯示狀態文字（見「錯誤」）
- **AC18** — 本文帶有 `subStatus` `4005`（「Asset is not ready for playback」）的 `401` 會原封不動地交還給呼叫端（即 `Response`，讓呼叫端能對應它，例如對應到 spec 0003 的 `StreamError::NotAvailable`），**不**更新也不重試。其他每個 `401` 維持 AC5 的更新一次並重試一次（見「錯誤」）
- **AC19** — 更新用的 client：更新請求的 `client_id`/`client_secret` 是 PKCE client 的（以測試資料檢查表單欄位），無論是一般更新，或是 `login` 在 device-flow 授權之後、儲存工作階段之前立即做的那一次更新。PKCE 更新被回答 `400`/`401` 且為 `invalid_client` 或 `unauthorized_client` 時，會以 device-flow client 重試一次，用那個權杖成功，並記錄一則警告；`invalid_grant` 維持 AC7 的「工作階段遺失」行為，且不會以另一個 client 重試。若登入後的更新因任何原因失敗，device-flow 授權會原樣儲存（一個可用但有損的工作階段）並印出警告。警告說明後果（CD 音質的曲目會以 AAC 串流）而不指名原因，因為它也涵蓋服務中斷與其他失敗
- **AC15** — `format!("{session:?}")` 不含任何一個權杖的值；每個變體的 `AuthError` 其 `Display` 都不含權杖，即使它是由回顯了權杖的伺服器本文建構的

<a id="edge-cases--errors"></a>
## 邊界情況與錯誤

- **`login` 期間按 Ctrl-C**：輪詢迴圈被取消，不儲存任何東西，結束碼 130
- **代碼在核准前過期**：`Login code expired, run "tidal-player login" again`，結束碼 1（AC2）
- **使用者在 Tidal 頁面上拒絕**：`Login was denied`，結束碼 1（AC2）
- **`login` 期間沒有網路**：輪詢把傳輸錯誤視為暫時性並持續輪詢直到 `expires_in`；開始請求失敗時以 1 結束並帶出傳輸錯誤
- **OAuth 錯誤代碼以外的輪詢回應**：`5xx` 與 `429` 算作「尚未」，與傳輸錯誤相同；任何其他非 `200` 都以 `AuthError::Http` 結束登入（只有在 OAuth `error` 代碼是已知的時候才帶著它，絕不帶本文）
- **輪詢期限**：從開始輪詢時算起；最後一次輪詢可能超過 `expires_in` 最多一個間隔
- **儲存更新後的工作階段失敗**（儲存位置無法使用、磁碟已滿）：記錄為警告；請求以記憶體中更新後的工作階段繼續，下一次更新會再試著儲存
- **沒有 `refresh_token` 的登入回應**（從未在實際環境見過）會得到 refresh 權杖為空的工作階段；它的第一次更新會被拒絕，行程進入「工作階段遺失」，告訴使用者重新登入
- **時鐘偏差**：到期時間是在收到時由 `expires_in` 計算，不是由伺服器的時間戳記；60 秒的餘裕加上被動的 401 路徑涵蓋小幅偏差
- **Secret Service 已鎖定**：視為不可用（常駐程式不會有解鎖提示），所以使用檔案後備方案。之後解鎖不會遷移工作階段；載入時兩個儲存位置都會讀取
- **任一儲存位置中損毀／不認得的資料**：視為未登入（AC10）
- **忘記密碼**：`tidal-player logout` 不問密碼就刪除加密檔案；然後 `login` 重新開始（AC10）
- **第一次輪詢的傳輸錯誤**曾在真實 API 上發生一次（curl 沒有得到回應），而之後以相同請求的輪詢都成功：輪詢期間的傳輸錯誤是暫時性的（見「`login` 期間沒有網路」）
- **常駐程式中的密碼錯誤**（密碼檔已過期）：以 1 結束並印出 `Wrong passphrase for the session file`，而不是「未登入」，這樣工作階段檔案絕不會被誤蓋（AC10、AC16）
- **密碼檔可被其他人讀取**：警告（`passphrase file is readable by other users`）但仍使用
- **常駐程式執行時 `logout`**：常駐程式下一次更新或 401 會碰到「工作階段遺失」（AC7）；它的下一次 `login` 會被取用（AC9）
- **免費／非 HiFi 帳號**：登入成功；它們能串流什麼是 spec 0003 的事

## Crate 配置

- `tidal-player-core`：`Event::LoginRequired`/`LoginRestored`、UI 狀態列。沒有 HTTP，沒有儲存
- `tidal-player-api::auth`：`Session`、`DeviceCode`、`PollOutcome`、`AuthError`、純粹的分類器、`SessionStore` trait 加 `MemoryStore`（供測試用，也作為建構元件）、`Authenticator`。基底 URL 是注入的（`auth_base`、`api_base`）；正式環境的 URL 以具名常數提供

- 新的 workspace 相依套件：`keyring`、`directories`、`age`（scrypt 密碼加密，純 Rust）、`rpassword`（關閉回顯的提示）、`zeroize`、`tempfile`（dev）、`webbrowser` 或 `open`（用來開啟 URL；失敗則忽略）。`xtask layering` 對 `core` 的禁用清單已涵蓋 `keyring`

<a id="facts-vs-assumptions"></a>
## 事實與假設

2026-10-06 由 `scripts/tidal-auth-probe.sh` 針對**真實 API** 驗證，由使用者以真實帳號執行（權杖與 ID 已遮蔽；`crates/api/tests/fixtures/auth/` 下的測試資料是依這些格式以假值寫成的）：

- **Device authorization** `200`：`{deviceCode, userCode (5 chars), verificationUri: "link.tidal.com", verificationUriComplete: "link.tidal.com/<userCode>", expiresIn: 300, interval: 2}`。開啟 `https://link.tidal.com` 並輸入代碼可行
- **Pending 輪詢**：`400 {"error":"authorization_pending","error_description":"Device Authorization code is not authorized yet","status":400,"sub_status":1002}`。沒有見到 `slow_down`
- **已授權** `200`：`{access_token, refresh_token, token_type, expires_in: 14400, scope, clientName: "Android Automotive HiRes", user_id: <number>, user: {userId, countryCode, email, username, …}}`。access 權杖持續 **4 小時**
- **更新** `200`：相同的格式但**沒有 `refresh_token`**：Tidal 不輪替它，原本的仍然有效
- **錯誤的 refresh 權杖**：`400 {"error":"invalid_grant","error_description":"Token has invalid payload","status":400,"sub_status":1005}`
- **帶有錯誤 bearer 的 API 呼叫**（`GET /v1/sessions`）：`401 {"status":401,"subStatus":11002,"userMessage":"Token has invalid payload"}`：API 錯誤的本文格式與 `/token` 錯誤不同，且沒有 `error` 鍵
- **撤銷**（`POST /revoke`，basic auth，如 tidalt 所做）：`403 {"error_description":"Request not allowed","status":403,"sub_status":1005}`，且 refresh 權杖之後仍能更新（`200`）。撤銷對這個 client 無效
- `GET /v1/sessions` 可行（`userId`、`countryCode`、`sessionId`……），但沒有加入任何權杖回應所缺少的東西
- 在 `device_authorization` 之後的第一次輪詢出現過一次傳輸失敗（沒有 HTTP 回應）；之後的輪詢都正常

未驗證，以及本規格如何應對：

- `slow_down`、`expired_token`、`access_denied` 的本文：假設是 RFC 8628 的錯誤代碼，與 `authorization_pending` 相同的 `{"error":…}` 格式；測試資料是依該格式手寫的並標示為手寫
- `verificationUriComplete` 是否預先填入代碼：只用於瀏覽器，印出的說明不依賴它
- Tidal 在伺服器端真正使其過期或失效的 refresh 權杖所得到的回應（無法產生，因為撤銷被拒絕）：假設是上述的 `invalid_grant` 格式
- Linux 上的 `keyring` 4 不需原生函式庫就能透過 D-Bus 連到 Secret Service，並把「沒有提供者」以可區分的錯誤回報（AC11 需要）

## 錯誤

- **狀態列在極小的終端機上 panic（2026-10-07 於 PR 審閱中發現）。** 預期：TUI 在任何尺寸下都能繪製（極小的終端機是列出的邊界情況類別）。實際：設定了登入狀態列時，`render` 以 `u16` 計算狀態列為 `area.height - 2`，在 0 或 1 列的終端機上會溢位（debug 建置會 panic），在 2 列時則蓋掉上邊框。根本原因：AC14 只修好了 80×24 的情況，所以座標運算從未針對小區域檢查過。新條件：AC17
- **每個 `401` 都會觸發更新，包括與權杖無關的（2026-10-07 由 spec 0003 的 probe 發現）。** 預期：只有表示「權杖錯誤或過期」的 `401` 才會更新。實際：AC5 對任何 `401` 都更新並重試，但當曲目或音質對帳號不可用時，Tidal 也會以 `subStatus` `4005`（「Asset is not ready for playback」）回答 `401`。那時權杖是好的，所以更新是白費的，重試得到相同的 `401`，呼叫端看到的是 `AuthError::Unauthorized` 而不是「不可用」。根本原因：「事實與假設」的 probe 只見到權杖錯誤的 `401`（`subStatus` `11002`），而規格假設每個 `401` 都是那樣。新條件：AC18，與 spec 0003 一起實作
- **CD 音質的曲目以 AAC 而不是 FLAC 串流（2026-10-07 由 spec 0003 的 probe 發現）。** 預期：HiFi/Max 帳號要求 `LOSSLESS` 時會得到 16 位元 FLAC。實際：發給 device-flow client `fX2JxdmntZWK0ixT` 的權杖，對 `LOSSLESS` 得到的是 `audioQuality: HIGH`（AAC 320），每首曲目都是如此。根本原因：自 2026 年 4 月下旬起，Tidal 把該 client ID 在 16 位元等級上限制為 AAC（python-tidal issue #404、streamrip #966）；hi-res 不受限制。修正，由 `scripts/tidal-playback-probe2.sh` 在真實環境驗證：用 PKCE client `6BDSRdpK9hqEBTgU` 更新**同一個** refresh 權杖會回傳 `200`（`clientName` 為「TIDAL_Android_2.87.0」，沒有新的 refresh 權杖），而該 access 權杖對 `LOSSLESS` 得到 DASH FLAC 16-bit/44.1 kHz，對 `HI_RES_LOSSLESS` 仍得到 FLAC 24/96。原本的 client 之後仍可更新同一個 refresh 權杖，所以改用它不會損失任何東西。sleezer（PR #174）與 hifi-api 也使用相同的變通方式。登入本身仍是 device flow。新條件：AC19，與 spec 0003 一起實作
- **被永久拒絕的登入 client 會無止境地更新（2026-10-07 於 PR 審閱中發現）。** 預期：當 PKCE client 與 device-flow client 都被拒絕時，工作階段即遺失，播放器要求登入。實際：device-flow 更新被回答 `unauthorized_client` 時落入「任何其他回應」而被視為暫時性，所以每個 API 呼叫都送出兩個更新請求，且永遠到不了 `LoginRequired`。根本原因：「更新失敗時」表格在 client 拒絕代碼中只列出 `invalid_client`。表格現在把 `unauthorized_client` 也列為「工作階段遺失」（AC7）
- **有損工作階段的警告把任何失敗都怪到 PKCE client 頭上（2026-10-07 於 PR 審閱中發現）。** 預期：`login` 保留 device-flow 權杖時顯示的警告，不論是什麼讓登入後的更新失敗，都是真實的。實際：在 `503` 或網路錯誤之後，它也說「Tidal did not accept the PKCE client」。根本原因：為 client 被拒絕的情況寫的一則訊息，被重用於「任何原因」。AC19 現在規定警告只指名後果
